# RepoSync

Приложение для синхронизации Git-репозиториев.

## Запуск и настройка

Нужны Node.js **22.14+** и системный Git в `PATH`. Авторизацию внешнего Git настройте через SSH Agent или Git Credential Manager вне RepoSync.

```sh
npm ci
npm run dev
```

Нажмите «Добавить репозиторий», укажите локальную папку Git и ветку. При необходимости подключите дополнительный Git-источник. Настройки источника, фильтры и формат данных доступны в профиле репозитория.

## Обновление приложения

Номер установленной версии виден рядом с названием приложения и в настройках: `v1.0.1` для main, `v1.0.1 · имя-ветки` для других веток. Выбор ветки обновления не меняет подпись текущей сборки.

При запуске RepoSync автоматически проверяет выбранную ветку. Если её коммит отличается от коммита работающей сборки, на главной появляется «Обновить приложение». В настройках можно выбрать ветку и вручную нажать «Проверить обновление». Кнопка «Обновить и перезапустить» появляется только при доступной версии. Фоновая проверка не блокирует работу с проектами и сама ничего не устанавливает.

Исходники определяются автоматически: сохранявшаяся папка, расположение приложения внутри repo-sync или служебная копия в папке данных. Невалидный старый путь не удаляется: приложение находит другой источник. Нужны Git и Node.js 22.14+ с npm; команда сборки выбирается из package.json под macOS/Windows. Несохранённые изменения, незавершённые Git-операции и расходящаяся история останавливают установку. Новая версия собирается отдельно, заменяет текущую после закрытия процесса и запускается; предыдущая сохраняется рядом. Для папки установки нужна запись.

На Windows заменяется папка установленного приложения (или win-unpacked) с сохранением штатного деинсталлятора; записи установщика в реестре не обновляются. Настройки и резервные копии RepoSync в папке данных не переносятся и не удаляются.

## Синхронизация

Выберите репозиторий и источник, просмотрите изменения, отметьте нужные файлы и проверьте результат перед применением. Если выбранные версии или файлы изменились после проверки, выполните сравнение повторно.

Приложение сохраняет резервную копию перед записью. Git-коммит и push выполняются пользователем отдельно.

## Восстановить предыдущие файлы

После применения доступна кнопка «Восстановить предыдущие файлы». Позже, включая после перезапуска, откройте «Резервные копии и восстановление» в подробностях карточки или на странице репозитория. Выберите операцию по дате, типу и ветке, посмотрите список путей и подтвердите восстановление. При большом наборе показаны первые 1000 путей, но восстановление затрагивает весь набор операции.

Восстановление возвращает только файлы и права этой операции: заменённые/удалённые версии возвращаются, созданные файлы удаляются. Git index, история и текущие настройки сохраняются; сведения синхронизации этого профиля сбрасываются. Состояние перед восстановлением тоже сохраняется в новой копии. Последующие изменения файлов или прав, другая ветка и повреждённая копия останавливают восстановление до записи.

Копии хранятся в `backups/<UUID>` внутри папки данных RepoSync; точное расположение показано в списке. `.bin` содержат исходные байты, `journal.json` связывает их с путями и правами. Новые журналы версии 3 дописывают ход операции в `progress.log`; эта версия читает прежние журналы и копии версии 2. Для новых копий используйте RepoSync 1.0.12 или новее: более ранние версии не поддерживают этот формат. Старые копии без сведений о ветке и итоговых правах сохранены и видны, но автоматическое восстановление для них недоступно. Автоматический откат прерванных операций старого формата сохраняется.

## Подготовка изменений

Выберите версии Git или рабочую копию, отметьте файлы и проверьте состав. Приложение создаст данные для синхронизации. Для применения подготовленных данных выберите их в приложении и проверьте результат.

## Проверка данных и просмотр

Входящие сравнения используют committed состояния выбранных веток. Исходящий режим коммита не включает рабочие изменения; режим рабочей копии включает текущие версии выбранных файлов. КБ-проверка рассматривает полные версии только выбранных исходящих файлов, включая содержимое переименований. Значения видны в просмотре; просмотр ничего не удаляет из пакета.

Проверка данных показывает дерево файлов пакета и совпадения выбранного файла. Найдите файл поиском или включите фильтр «Только требующие решения». «Принять файл» оставляет нерешённые значения исходными; ранее выбранные замены сохраняются. «Заменить нерешённые на *» меняет значения только в выгрузке; исходники и Git не изменяются. Каждое совпадение также можно решить отдельно. Файл можно исключить и вернуть вместе с его решениями; исключения правил нельзя отменить вручную. Нижняя сводка показывает состав пакета, замены и оставшиеся решения. Scanner может пропустить чувствительные данные или отметить безопасный пример.

Галочки папок и «Выбрать показанные»/«Снять показанные» затрагивают только показанные доступные файлы, сохраняя выбор вне поиска. Переименование выбирается целиком. Поиск и фильтры CRLF/LF, отступов/краёв строк, пустых строк и «как compare-projects» меняют только просмотр, не выбранный набор или перенос. Последний режим также сворачивает пробелы внутри строк и не доказывает равнозначность кода.

Просмотр поддерживает поиск, сравнение рядом и единый список. Для бинарных файлов и файлов больше 128 КБ вместо кода показаны наличие, размер, права и результат операции. Отмеченные расхождения не скрываются фильтрами пробелов. SHA и технические сведения находятся в «Подробности»; доступны светлая и тёмная темы.


## Общие и проектные фильтры

В настройках программы задайте шаблон glob-исключений, по одной маске на строку: например `**/*.test.*`, `**/*.snapshot`, `**/__snapshots__/**`. В «Настройках просмотра» рабочего экрана доступны унаследованные правила с переключателями и дополнительные маски проекта. «Сбросить настройки проекта» возвращает наследование. Правила сохраняются и применяются при подготовке пакета, получении из Git и применении пакета. Путь относительно корня, разделитель `/`, dot-файлы учитываются; отрицание `!` не поддерживается.

Совпавшие файлы остаются видимыми отключёнными: их нельзя выбрать, они не отправляются и не применяются. При переименовании учитываются оба пути. Снятие маски делает файл доступным, но не выбирает его автоматически. Изменение правил пересчитывает сравнение и сбрасывает готовность применения. Фильтры пробелов остаются отдельными настройками только просмотра.

## Сведения о проектах

Главный экран показывает тип и дату последнего успешного действия, состояние локального Git (текущая/настроенная ветка, SHA, дата коммита, рабочая копия) и загруженного внешнего Git. Фоновая проверка выполняется в простое при открытии приложения, возврате фокуса и раз в пять минут. Она использует список удалённых SHA, не загружает коммиты и не меняет рабочую копию. «Есть обновление» означает, что SHA отличается от кэша; кнопка «Обновить» загружает внешний Git только в кэш RepoSync. Ошибки и время последней успешной проверки показываются отдельно. Пока идёт работа с переносом, новые фоновые проверки не запускаются; устаревшие ответы отбрасываются.

Настройки v6 мигрируют прежние версии с резервной копией исходного JSON; прежние baseline, pending и legacy scope сохраняются. Типы действий включают сравнение, проверку данных, настройки, создание/применение пакета, подтверждение передачи и обновление кэша. Фоновые проверки не перезаписывают дату действий пользователя.

## Формат и совместимость

В подготовке пакета есть «Включать изображения в пакет», по умолчанию включено для новой сессии. Выключение исключает изображения, их удаления и переименования целиком; повторное включение возвращает индивидуальный выбор. SVG тоже считается изображением. Остальные файлы и существующие изображения получателя сохраняются. Код может ссылаться на исключённый ресурс: наличие зависимостей у получателя проверяйте отдельно.

Обычные пакеты используют protocol/schema **v6** с полными байтами выбранных изменённых файлов и без патчей. При сравнении внутренних версий A → B создаётся пакет **v7** с исходными байтами изменённых файлов для слияния с независимыми локальными правками. Непересекающиеся текстовые изменения объединяются автоматически; пересечения, бинарные и неоднозначные изменения требуют явного решения. Текст открыт внутри `.md`; бинарные версии передаются отдельными вложениями с исходными байтами и расширением. Переносите все части и вложения вместе. Отсутствующие бинарные вложения v5–v7 показываются предупреждением; отсутствующая исходная версия v7 блокирует загрузку. Повреждённые вложения блокируют загрузку. Base64, сжатия и шифрования при экспорте нет. V6 убирает повторяющееся описание файлов и вычисляемые поля; v7 сохраняет проверки размера и SHA256 для конечной и исходной версий. Compact минифицирует служебные JSON-метаданные; readable добавляет заголовки блоков. Кроме явно выбранных замен чувствительных значений на звёздочки в конечной версии, содержимое файлов сохраняет LF/CRLF, отступы, пробелы, BOM и executable mode. Исходный Base64 в самих файлах также сохраняется. Размер части ограничивает `.md`; бинарное вложение остаётся целым, общий предел пакета — 512 МиБ.

Для новых пакетов обновите RepoSync на обеих сторонах. Импорт v1–v6 сохранён с прежними правилами каждого формата; v2 также требует своих исходных бинарных вложений. Старые ожидания подтверждения сохраняют прежнее поведение. Настройки остаются v6; миграция v1–v5 сохраняет исходный JSON рядом с `settings.json`.

## Где RepoSync хранит данные

Пути указаны для обычной установки. `<данные>` — это `~/Library/Application Support/RepoSync` на macOS и `%APPDATA%\RepoSync` на Windows.

| Путь | Что хранится |
| --- | --- |
| `<данные>/settings.json` | Профили, пути и ветки репозиториев, фильтры, папка экспорта, сведения о синхронизации и пакетах, ожидающих подтверждения. |
| `<данные>/settings.vN.backup.json` | Копия прежних настроек, созданная при миграции формата. |
| `<данные>/git-cache/<хеш>/` | Локальная Git-копия внешнего источника: объекты, ссылки и история. Рядом могут быть файлы со списками веток. |
| `<данные>/git-cache/sync-bytes/` | Байты файлов сохранённого состояния синхронизации. Их отсутствие может потребовать первичной синхронизации. |
| `<данные>/backups/<UUID>/` | Исходные версии изменённых файлов и журналы для отката и восстановления. |
| `<данные>/Cache/`, `Code Cache/`, `GPUCache/` и подобные | Кэши Electron/Chromium. |
| `<данные>/Local Storage/` и другие хранилища Electron | Данные браузерного сеанса; в `Local Storage` сохраняется выбранная тема. |
| `<данные>/app-update-source.txt`, `app-source*`, `app-build-*` | Путь к исходникам приложения, возможная управляемая копия исходников и файлы сборки обновления. |
| Папка экспорта из настроек (`outputDirectory`) | Созданные части пакетов `.md` и бинарные вложения. Папку выбирает пользователь. |
| Выбранный локальный Git-репозиторий | RepoSync изменяет выбранные файлы при применении пакета и может переключать ветку Git. Во время записи рядом с файлами появляются временные `.reposync-*.tmp`. |
| Системная временная папка, `reposync-merge-*` | Временные файлы текстового слияния; обычно удаляются после операции. |

Удаление `<данные>` сбрасывает состояние RepoSync и удаляет его резервные копии, но не удаляет экспортированные пакеты, установленное приложение и выбранные Git-репозитории. При сборке из исходников дополнительно используются `node_modules/`, `dist/` и `release/` в папке проекта, а также общие кэши npm и Electron.

## Сборка

```sh
npm run build
npm start
```

Для `.app`/DMG/ZIP: `npm run dist:mac`; для Windows: `npm run dist:win`. Результат в `release/`. Сборка исходников не обновляет ранее скопированное приложение. Подпись настраивается отдельно; автоматического обновления нет.

## Настройка репозитория и локальный Git

Для каждого репозитория укажите локальную папку Git и ветку. Дополнительный Git-источник можно подключить позже.

При выборе папки RepoSync считывает текущую ветку. В существующем профиле выбранная ветка сохраняется; текущая ветка показывается отдельно. Перед применением видны обе ветки, HEAD, локальные изменения и незавершённые операции. В карточке можно быстро переключиться на выбранную ветку. В обзоре репозитория и на этапах переноса можно выбрать любую существующую локальную ветку и нажать «Переключить на выбранную ветку»: фактическое переключение требует чистой копии, без автоматического сохранения или удаления правок. Если ветка уже открыта, «Использовать открытую ветку» меняет цель синхронизации в профиле без смены рабочей копии. После этого сравнение обновляется и сохраняет выбор файлов, которые остаются в новом списке.

Просмотр и применение доступны при локальных изменениях. Перед применением показаны затронутые незакоммиченные файлы; для их перезаписи нужна галочка «Разрешаю перезаписать перечисленные локальные изменения». Совпадающий результат не требует записи и подтверждения. Изменение выбранных файлов, их Git-статуса или HEAD после просмотра требует повторной проверки и нового согласия. Завершите или отмените незавершённые операции своими Git-инструментами, затем нажмите «Проверить снова». При detached HEAD выберите существующую ветку и переключитесь на неё. Перед записью повторяются проверки ветки, HEAD и файлов. Не изменяйте репозиторий параллельно с применением.

После применения изменения находятся в рабочей копии: проверьте результат и создайте коммит. Подтверждение передачи пакета завершает ожидание; оно не означает, что рабочая копия чистая или репозитории одинаковы.
