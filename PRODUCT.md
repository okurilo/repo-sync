# RepoSync — контекст продукта

## Platform

web

Интерфейс React внутри настольного Electron-приложения для macOS и Windows. Значение `web` описывает технологию и язык интерфейса; продукт используется как настольное приложение, а не как публичный сайт.

## Users

Основной пользователь — разработчик, который переносит выбранные изменения между уже существующими внешним и изолированным корпоративным Git-репозиториями.

## Product Purpose

Получать внешние изменения во внутренний репозиторий и передавать внутренние изменения во внешний контур через локальные пакеты. Успешный перенос сохраняет точные байты выбранных файлов и оставляет невыбранные пути без изменений; пользователь видит результат до применения и самостоятельно создаёт commit и выполняет push.

## Positioning

RepoSync связывает два изолированных контура через выбор файлов, просмотр отличий и перенос полных версий файлов. Общая Git-история для нового исходящего пакета не требуется. История Git и `.git` не переносятся. Содержимое нового экспорта открыто для проверки корпоративными DLP-системами; прохождение проверки конкретной системой не гарантируется.

## Operating Context

- «Внутренний» и «Внешний» — контуры отдельного профиля репозитория. Во внутреннем профиле настроены локальная папка Git и внешний Git-источник; во внешнем достаточно локальной папки Git.
- Входящий сценарий: сравнить внешние изменения, выбрать файлы, проверить применение и применить. После проверки просмотр показывает локальное содержимое «До» и готовую версию «После».
- Исходящий сценарий: сравнить внутренний committed HEAD с выбранным внешним HEAD, выбрать файлы, рассмотреть найденные чувствительные данные при наличии и создать пакет.
- Пользователь передаёт все части `.md` и бинарные вложения вместе. Во внешнем контуре выбирает пакет, проверяет выбранные изменения и применяет их.
- Подтверждение передачи завершает ожидание, но не означает равенство репозиториев. После применения пользователь проверяет рабочую копию и создаёт commit своими Git-инструментами.
- Авторизация внешнего Git настраивается вне RepoSync. Нужен системный Git; локальный запуск разработки описан в `README.md` и выполняется через `npm run dev`.

## Capabilities and Constraints

- Основные сценарии используют committed состояния. Staged, unstaged и untracked изменения не включаются в пакет.
- Перед применением требуется чистая локальная рабочая копия на выбранной ветке без незавершённых операций Git. Перед записью повторяются проверки ветки, HEAD и файлов, создаётся резервная копия; предусмотрено восстановление незавершённого применения.
- Изменяемые выбранные файлы переносятся целиком. Сохраняются байты, LF/CRLF, отступы, пробелы, BOM, отсутствие завершающего переноса и executable mode.
- Новый экспорт не добавляет Base64, сжатие, шифрование, обфускацию или другие способы скрыть содержимое от DLP. Уже существующий Base64 внутри исходного файла сохраняется как исходное содержимое.
- Текст находится открыто в `.md`; бинарные файлы — отдельные вложения с исходными байтами. Компактный режим уменьшает только служебные метаданные. Общий предел пакета — 512 МиБ.
- Проверка чувствительных данных выполняется для выбранных исходящих файлов. Scanner может ошибаться; потенциальные секреты требуют отдельного явного решения. Во входящем сценарии КБ-проверки нет.
- Просмотр не маскирует исходные значения и не меняет передаваемые данные. Поиск и фильтры отличий влияют только на просмотр. Удаления в исходящем сценарии по умолчанию не выбраны.
- Автоматические commit/push, telemetry и auto-updater не предусмотрены. Нет автоматического сетевого канала между контурами.
- Symlinks, submodules и неподдерживаемые пути или переходы типов файлов отклоняются, а не эмулируются молча.
- Дополнительные продуктовые требования доступности и конкретный стандарт соответствия пока не определены.

## Brand Commitments

Название — RepoSync. Интерфейс и пользовательские объяснения — на русском языке. Термины «Внутренний», «Внешний», «Получить изменения» и «Подготовить пакет изменений» описывают контур и действие. Текст должен ясно объяснять результат действия, причину отказа и следующий шаг.

## Evidence on Hand

- `README.md` — текущие пользовательские сценарии, запуск и формат передачи.
- `CODEX-RULES.MD` — обязательные ограничения, включая прозрачность экспорта для DLP.
- `CODEX.MD` — инженерные решения и история отменённых подходов; новые записи уточняют прежние.
- `docs/SDD.md`, `docs/specs/` и `docs/ADR/` — устройство и контракты продукта.
- `docs/manual-qa.md` — выполненные проверки и ограничения подтверждённого покрытия.
- `src/renderer/` — существующий интерфейс; `package.json` — стек и команды сборки.

Не приписывать продукту неподтверждённые сертификаты DLP, гарантии scanner или результаты проверки платформ, отсутствующие в документации.

## Product Principles

1. Пользователь явно выбирает переносимые изменения и контролирует последствия применения.
2. Точность файлов и прозрачность содержимого важнее компактности пакета.
3. При неопределённости или конфликте остановить запись и объяснить причину; не подменять сценарий молча.
4. Сохранять границы контуров и оставлять управление Git-историей пользователю.
5. Использовать минимальный надёжный механизм без дополнительных слоёв и скрытых побочных эффектов.
